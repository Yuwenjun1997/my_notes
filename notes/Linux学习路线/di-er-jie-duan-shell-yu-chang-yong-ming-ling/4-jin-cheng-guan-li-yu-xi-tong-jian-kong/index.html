一、进程基础概念

1.1 进程与线程

进程（Process）：正在运行的程序实例，拥有独立的内存空间。
线程（Thread）：进程内的执行单元，共享进程的内存空间。

PID (Process ID)：唯一标识一个进程的数字。
PPID (Parent PID)：父进程的 PID。

1.2 进程状态

状态码含义说明
RRunning/Runnable正在运行或在运行队列中等待
SSleeping (可中断)等待事件（I/O、信号等）
DUninterruptible Sleep等待 I/O 完成，不可被信号中断
ZZombie僵尸进程，子进程已退出但父进程未回收
TStopped被信号暂停（如 Ctrl+Z）

二、进程查看

2.1 ps — 查看进程快照

# BSD 风格（带 -）
ps -ef                       # 显示所有进程完整信息
ps -ef | grep java           # 查找 Java 进程

# Unix 风格（不带 -）
ps aux                       # ⭐ 最常用：所有用户的详细进程
ps aux --sort=-%mem          # 按内存占用排序
ps aux --sort=-%cpu          # 按 CPU 占用排序
ps aux | head -1; ps aux --sort=-%mem | head -10  # 内存 Top 10

# 自定义输出
ps -eo pid,ppid,user,%cpu,%mem,cmd --sort=-%cpu   # 自定义列

ps aux 输出字段解释：

USER   PID  %CPU %MEM    VSZ   RSS TTY  STAT  START   TIME  COMMAND
root     1   0.0  0.1  22548  3484 ?    Ss    10:00  0:01  /sbin/init
①       ②    ③    ④     ⑤    ⑥   ⑦    ⑧     ⑨     ⑩     ⑪

① 用户名     ② 进程 ID      ③ CPU 使用率（%）
④ 内存使用率  ⑤ 虚拟内存(KB)  ⑥ 物理内存(KB)
⑦ 终端       ⑧ 进程状态      ⑨ 启动时间
⑩ 累计 CPU 时间 ⑪ 命令行

2.2 top / htop — 实时监控

top                    # 实时进程监控（按 q 退出）
htop                   # 更友好的 top（需安装：sudo apt install htop）

# top 交互快捷键：
#   1      显示每个 CPU 核心的使用率
#   M      按内存使用率排序
#   P      按 CPU 使用率排序
#   k      输入 PID 以杀死进程
#   f      选择显示的列
#   c      显示完整命令行
#   q      退出

2.3 查看特定进程

# 按 PID 查看
ps -p 1234 -f                             # 查看 PID 1234 的详细信息

# 按名称查找
pgrep -a java                             # 查找所有 java 进程
pidof nginx                               # 查找 nginx 的 PID

# 查看进程树（父子关系）
pstree -p                                 # 显示所有进程树
pstree -p 1234                            # 显示 PID 1234 的子进程树
pstree -p -u alice                        # 显示 alice 用户的进程树

2.4 查看端口占用

# ⭐ 最常用：查看端口被哪个进程占用
sudo lsof -i :8080                        # 端口 8080
sudo lsof -i :80,443                      # 多个端口

# ss — 查看 socket 连接
ss -tlnp                                  # 查看所有 TCP 监听端口
ss -tlnp | grep :8080                     # 查看 8080 端口
ss -anp | grep ESTAB                      # 查看所有 ESTABLISHED 连接

# netstat — 传统工具（需安装 net-tools）
netstat -tlnp | grep :8080
netstat -anp | grep ESTABLISHED | wc -l   # 统计活跃连接数

⚠️ 端口占用排查：lsof -i :端口号 是最直接的方式，ss 在 Ubuntu 上通常已预装。

三、进程控制

3.1 信号（Signal）

Linux 通过信号与进程通信：

信号编号信号名作用可捕获？
1SIGHUP挂起（常用于重新加载配置）是
2SIGINT中断（Ctrl+C）是
3SIGQUIT退出（Ctrl+\）并生成 core dump是
9SIGKILL强制杀死（不可捕获）❌
15SIGTERM优雅终止（默认）是
19SIGSTOP暂停进程❌
18SIGCONT恢复暂停的进程是

3.2 kill / pkill — 发送信号

# kill — 按 PID 发送信号
kill PID                     # 发送 SIGTERM（默认，优雅终止）
kill -15 PID                 # 同上，显式指定 SIGTERM
kill -9 PID                  # ⚠️ 强制杀死（不给进程清理机会）
kill -l                      # 列出所有信号
kill -HUP 1234               # 发送 SIGHUP（常用于重新加载配置）

# pkill — 按名称发送信号
pkill java                   # 终止所有 java 进程
pkill -f "spring-boot"       # 按完整命令行匹配
pkill -HUP nginx             # 重新加载 nginx 配置

# killall — 按进程名终止
killall -9 java              # 杀死所有名为 java 的进程

⚠️ 注意事项：

  • 优先使用 kill -15（优雅终止），给进程机会释放资源、关闭连接
  • kill -9 是最后手段，进程无法拒绝，但可能导致数据丢失
  • kill -9 杀不掉的进程通常处于 D 状态（等待 I/O），只能等 I/O 完成或重启

3.3 前台与后台运行

# 后台启动
java -jar app.jar &                   # 末尾加 & 后台运行
nohup java -jar app.jar &             # 忽略 SIGHUP，关闭终端后继续运行

# ⭐ 推荐：使用 nohup + 输出重定向
nohup java -jar app.jar > app.log 2>&1 &

# 任务管理
jobs                                  # 查看当前 Shell 的后台任务
Ctrl+Z                                # 暂停前台进程
bg %1                                 # 将暂停的任务放到后台继续
fg %1                                 # 将后台任务调到前台
disown %1                             # 将后台任务从 Shell 任务列表中移除

# 简单守护进程（Ubuntu）
setsid java -jar app.jar > app.log 2>&1 &

三种后台运行方式对比：

方式关闭终端后适用场景
cmd &❌ 被杀死临时后台任务
nohup cmd &✅ 继续运行简单守护进程
systemd service✅ 继续运行 + 管理生产环境推荐

四、系统资源监控

4.1 内存查看

free -h                     # 人类可读格式 ⭐
free -h -s 2                # 每 2 秒刷新一次

# 输出解读：
#               total   used   free   shared   buff/cache   available
# Mem:          7.7G    2.1G   3.2G   180M     2.4G         5.1G
#
# total = 总内存     used = 已用（含 buffer/cache）
# available = 可用于新进程的内存 ⭐ 最重要
# buff/cache = 文件缓存（可被释放）

⚠️ 内存理解误区：Linux 会用空闲内存做文件缓存（buffer/cache），所以 free 列很小是正常的。真正关注的是 available 列，它表示还有多少内存可用。

4.2 磁盘查看

# 磁盘使用
df -h                                # ⭐ 查看分区使用情况
df -i                                # 查看 inode 使用情况
df -hT                               # 显示文件系统类型

# 目录占用
du -sh /home/                        # 查看目录总大小
du -sh * | sort -h                   # 当前目录下各文件/目录大小排序 ⭐
du -h --max-depth=1 /var/            # 显示一层子目录大小
du -ah /var/log/ | sort -h | tail    # 找出最大的文件

# 查找大文件
find / -type f -size +1G 2>/dev/null    # 查找大于 1G 的文件

4.3 CPU 与 I/O 监控

# CPU 信息
lscpu                                 # CPU 详细信息
cat /proc/cpuinfo | grep "model name" | uniq  # CPU 型号
nproc                                 # CPU 核心数

# 系统负载
uptime                                # 1/5/15 分钟平均负载
# 输出解读：12:34:56 up 10 days,  2:30,  3 users,  load average: 0.50, 0.30, 0.20
# load average: 1分钟平均 5分钟平均 15分钟平均
# 经验值：负载 < CPU 核心数 = 正常；负载持续 > 核心数 = 需要关注

# I/O 监控
iostat -x 1                           # 磁盘 I/O 统计（需安装 sysstat）
iotop                                 # 类似 top 的 I/O 监控（sudo iotop）
sudo apt install sysstat iotop -y     # 安装

五、systemd 服务管理

Ubuntu 使用 systemd 作为 init 系统，管理所有系统服务。

# ===== 服务状态 =====
systemctl status nginx                 # 查看服务状态
systemctl is-active nginx              # 检查是否运行中
systemctl is-enabled nginx             # 检查是否开机自启
systemctl list-units --type=service    # 列出所有服务
systemctl list-units --type=service --state=failed  # 查看失败的服务

# ===== 服务控制 =====
sudo systemctl start nginx             # 启动
sudo systemctl stop nginx              # 停止
sudo systemctl restart nginx           # 重启
sudo systemctl reload nginx            # 重新加载配置（不停机）⭐
sudo systemctl enable nginx            # 开机自启
sudo systemctl disable nginx           # 禁止开机自启
sudo systemctl mask nginx              # 禁止手动启动（更强的禁用）
sudo systemctl unmask nginx            # 取消 mask

# ===== 日志查看 =====
journalctl -u nginx                    # 查看 nginx 所有日志
journalctl -u nginx -f                 # 实时跟踪 ⭐
journalctl -u nginx --since "10 minutes ago"   # 最近 10 分钟
journalctl -u nginx --since "2024-06-22"       # 从指定日期
journalctl -u nginx -n 50              # 最近 50 条
journalctl -u nginx -p err             # 只看 ERROR 级别

六、进阶：僵尸进程、/proc 与资源限制

6.1 僵尸进程的产生与回收

# 僵尸进程（Z）：子进程已退出，但父进程没有调用 wait() 回收它的退出状态
# 产生原因：父进程 fork 后没 wait、或父进程本身是常驻服务没处理 SIGCHLD

# 找到所有僵尸进程 ⭐
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
ps aux | awk '$8 ~ /^Z/'

# 僵尸进程杀不掉（kill -9 无效），只能：
# 1. 让父进程处理：kill -HUP 父进程，或重启父进程（父进程退出后由 init 收养回收）
# 2. 如果父进程是 init(1)，僵尸会尽快被回收
kill -HUP <PPID>        # 提示父进程重新读取配置/回收子进程

💡 少量僵尸进程无害；大量僵尸说明父进程存在 bug（没 wait），排查方向是父进程，而不是僵尸本身。

6.2 /proc/PID/ —— 进程的"体检报告"

# 每个进程在 /proc 下都有一个目录，内核实时暴露进程信息 ⭐
PID=$(pgrep -f "app.jar" | head -1)

cat /proc/$PID/status        # 状态、内存、线程数（Threads 字段）
ls -l /proc/$PID/fd          # 该进程打开的所有文件描述符 ⭐
cat /proc/$PID/cmdline | tr '\0' ' '   # 完整启动命令行（含空格，用 \0 分隔）
cat /proc/$PID/environ | tr '\0' '\n'  # 进程的环境变量
cat /proc/$PID/limits        # 进程的资源限制（含 nofile 软硬上限）
ls /proc/$PID/task           # 该进程的所有线程

# 实时监控：/proc/meminfo /proc/loadavg /proc/cpuinfo
head -5 /proc/meminfo
cat /proc/loadavg

💡 排查"进程占了多少内存 / 打开了哪些文件 / 环境变量是什么"这类问题，/proc/PID/ 是最权威的第一手数据，比 top/ps 更细。

6.3 cgroup 与 systemd 资源限制

# systemd 运行任意命令并附加资源限制 ⭐
sudo systemd-run --scope -p MemoryMax=512M -p CPUQuota=50% java -jar app.jar

# 对已有服务设置资源上限（立即生效 + 写入配置）
sudo systemctl set-property nginx.service MemoryMax=1G
sudo systemctl set-property nginx.service CPUQuota=80%

# 查看 cgroup 实际用量
systemd-cgtop                    # 类似 top 的 cgroup 资源视图
cat /sys/fs/cgroup/memory.events # OOM 事件计数

💡 这是防止"单进程吃光内存/CPU"的现代做法，比 ulimit 更细粒度（可针对单个服务）。与 4.3 内核参数调优、4.4 容器资源限制衔接。

6.4 后台运行的会话细节与 tmux

# & vs nohup vs setsid 的差异核心：控制终端与 SIGHUP
#   cmd &            ：仍是当前会话的作业，关终端发 SIGHUP 被终止
#   nohup cmd &      ：忽略 SIGHUP，但没有完全脱离会话（3.3 已讲）
#   setsid cmd       ：创建新会话，完全脱离终端 ⭐

setsid java -jar app.jar > app.log 2>&1 &
disown -h %1          # 标记后台任务不响应 SIGHUP（配合 & 使用）

# ⭐ 推荐：长任务用 tmux/screen，会话级保持 + 可重连
sudo apt install tmux -y
tmux new -s deploy            # 新建会话（关终端任务继续跑）
tmux attach -t deploy         # 重新连接
tmux ls                       # 列出会话

💡 nohup 只能防 SIGHUP；tmux/screen 提供的是完整会话保持：中途断线可 attach 重连，还能看回历史输出。远程操作长时间任务首选。

6.5 ulimit 与 "Too many open files"

ulimit -n                    # 查看当前进程打开文件数上限
ulimit -n 65535              # 临时调高（当前会话）

# 永久设置（用户级）写入 /etc/security/limits.conf
# alice soft nofile 65535
# alice hard nofile 65535

# 服务级（systemd 服务）在 unit 文件里设
# [Service]
# LimitNOFILE=65535

# 全局内核上限
sysctl fs.file-max           # 系统所有进程可打开的 fd 总数

⚠️ "Too many open files" 是 Java/中间件高并发下的经典报错：连接数/文件句柄超过 ulimit -n 默认值（常为 1024）。排查顺序：ulimit -n → 服务是否降级了限制 → 提高软硬上限后重启服务。与 4.3 连接数排查、4.4 容器限制联动。

📝 实践项目

目标

掌握进程管理和系统监控的核心技能。

步骤

  1. 找出最占资源的进程

    # CPU Top 5
ps aux --sort=-%cpu | head -6

# 内存 Top 5
ps aux --sort=-%mem | head -6

  2. 端口排查实战

    # 启动一个测试服务
python3 -m http.server 8080 &

# 找到占用 8080 端口的进程
sudo lsof -i :8080
ss -tlnp | grep 8080

# 杀掉它
kill $(lsof -t -i:8080)

  3. 后台运行实验

    # 使用 nohup 保持后台运行
python3 -m http.server 8080 > /dev/null 2>&1 &
echo $!                         # 记录 PID
disown

# 验证：关闭终端再重新打开
curl localhost:8080             # 服务仍在运行

# 清理
pkill -f "http.server"

  4. 系统健康检查

    echo "=== 系统健康状况 ==="
echo "运行时间：$(uptime -p)"
echo "内存使用：$(free -h | awk '/Mem/ {print $3 "/" $2}')"
echo "磁盘使用："
df -h / | awk 'NR==2 {print $3 "/" $2 " (" $5 ")"}'
echo "CPU 负载：$(uptime | awk -F 'load average:' '{print $2}')"
