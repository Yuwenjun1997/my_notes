# 高并发限流与性能压测

> 深入限流算法与 asyncio 实现，掌握并发控制、性能定位与 locust 压测方法论，具备高并发服务的性能调优能力。

## 一、限流算法

### 1.1 固定窗口计数

**固定窗口**：将时间划分为固定长度窗口，每个窗口内计数，超过阈值即拒绝。实现最简单，但存在**窗口边界突发**问题。

```python
import time

class FixedWindowRateLimiter:
    """固定窗口限流器"""

    def __init__(self, limit: int, window_seconds: float):
        self.limit = limit                 # 窗口内最大请求数
        self.window = window_seconds       # 窗口时长
        self.window_start = time.monotonic()
        self.count = 0

    def allow(self) -> bool:
        now = time.monotonic()
        # 窗口过期则重置
        if now - self.window_start >= self.window:
            self.window_start = now
            self.count = 0
        if self.count < self.limit:
            self.count += 1
            return True
        return False
```

**窗口边界问题**：若一个窗口最后时刻放行 N 个，下一个窗口开始又放行 N 个，则短时间内可放行 2N 个请求，形成突发。

```
固定窗口缺陷示意（limit=5，窗口 1s）
 窗口1         窗口2
 |----X----|  |----X----|
     5个请求        5个请求
       └─ 边界处瞬时 10 个请求！
```

### 1.2 滑动窗口

**滑动窗口**：记录每个请求的时间戳，只统计「当前时间往前一个窗口长度」内的请求数，消除边界突发。

```python
import time
from collections import deque

class SlidingWindowRateLimiter:
    """滑动窗口限流器（基于时间戳队列）"""

    def __init__(self, limit: int, window_seconds: float):
        self.limit = limit
        self.window = window_seconds
        self.timestamps = deque()          # 按时间排序的请求时间戳

    def allow(self) -> bool:
        now = time.monotonic()
        # 清理窗口外的过期时间戳
        while self.timestamps and now - self.timestamps[0] >= self.window:
            self.timestamps.popleft()

        if len(self.timestamps) < self.limit:
            self.timestamps.append(now)
            return True
        return False
```

**优缺点对比**：

| 算法 | 内存开销 | 精度 | 突发容忍 | 实现复杂度 |
|:-----|:---------|:-----|:---------|:----------|
| 固定窗口 | O(1) | 低（有边界突发） | 高 | 简单 |
| 滑动窗口 | O(N) 请求数 | 高 | 低 | 中等 |
| 令牌桶 | O(1) | 中（允许突发到桶容量） | 中 | 简单 |
| 漏桶 | O(1) | 中（恒定速率） | 低 | 简单 |

### 1.3 令牌桶

**令牌桶**：以固定速率向桶中放入令牌，桶有容量上限；请求需取走令牌才被放行。允许一定程度的突发（桶满时），是业界最常用的限流算法（如 Guava、API 网关）。

```python
import time
import threading

class TokenBucketRateLimiter:
    """令牌桶限流器（线程安全）"""

    def __init__(self, rate: float, capacity: int):
        self.rate = rate                   # 令牌生成速率（个/秒）
        self.capacity = capacity           # 桶容量（最大突发）
        self.tokens = capacity             # 当前令牌数
        self.last_refill = time.monotonic()
        self._lock = threading.Lock()

    def allow(self) -> bool:
        with self._lock:
            now = time.monotonic()
            # 按时间补充令牌
            elapsed = now - self.last_refill
            self.tokens = min(self.capacity,
                              self.tokens + elapsed * self.rate)
            self.last_refill = now

            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False
```

### 1.4 漏桶

**漏桶**：请求先进桶，桶以**恒定速率**漏出处理，桶满则丢弃。输出速率恒定，无突发，适合「平滑流量」场景（如数据库写入限流）。

```python
import time
import threading

class LeakyBucketRateLimiter:
    """漏桶限流器：恒定速率流出"""

    def __init__(self, capacity: int, leak_rate: float):
        self.capacity = capacity           # 桶容量
        self.leak_rate = leak_rate         # 漏水速率（个/秒）
        self.water = 0                     # 当前水量
        self.last_leak = time.monotonic()
        self._lock = threading.Lock()

    def allow(self) -> bool:
        with self._lock:
            now = time.monotonic()
            # 先漏水
            self.water = max(0, self.water - (now - self.last_leak) * self.leak_rate)
            self.last_leak = now

            if self.water + 1 <= self.capacity:
                self.water += 1
                return True
            return False                     # 桶满，拒绝
```

## 二、asyncio 并发控制

### 2.1 Semaphore 并发限制

**asyncio.Semaphore**：限制同时执行的协程数量，是最常用的异步并发控制手段，等效于令牌桶的「并发上限」形态。

```python
import asyncio

class ConcurrencyLimiter:
    """基于信号量的异步并发限流器"""

    def __init__(self, max_concurrency: int):
        self.sem = asyncio.Semaphore(max_concurrency)

    async def run(self, coro_factory):
        async with self.sem:               # 获取许可，超过则等待
            return await coro_factory()

async def worker(i, limiter):
    # 模拟业务处理
    await asyncio.sleep(0.5)
    return i

async def main():
    limiter = ConcurrencyLimiter(max_concurrency=5)
    # 20 个任务，同时最多执行 5 个
    results = await asyncio.gather(
        *(limiter.run(lambda i=i: worker(i, limiter)) for i in range(20))
    )
    print(results)

asyncio.run(main())
```

### 2.2 基于时间的异步限流

**异步限流**：结合令牌桶思想与 asyncio 的「延迟放行」，控制请求在时间维度上的分布。

```python
import asyncio
import time

class AsyncTokenBucket:
    """异步令牌桶：令牌不足时等待补充（平滑放行）"""

    def __init__(self, rate: float, capacity: int):
        self.rate = rate
        self.capacity = capacity
        self.tokens = capacity
        self.last = time.monotonic()
        self._lock = asyncio.Lock()

    async def acquire(self):
        """获取一个令牌，不足则等待"""
        async with self._lock:
            while True:
                now = time.monotonic()
                self.tokens = min(self.capacity,
                                  self.tokens + (now - self.last) * self.rate)
                self.last = now
                if self.tokens >= 1:
                    self.tokens -= 1
                    return
                # 计算还需等待多少毫秒才能补足 1 个令牌
                await asyncio.sleep((1 - self.tokens) / self.rate)
```

### 2.3 限流在 FastAPI 中的应用

**接口限流**：通过中间件/依赖注入实现全局或按路由的限流，配合 Redis 可跨进程生效（多 worker 场景）。

```python
from fastapi import FastAPI, Request, HTTPException
import time

app = FastAPI()

# 简单的进程内滑动窗口限流中间件
class SimpleRateLimitMiddleware:
    def __init__(self, limit: int = 100, window: float = 60.0):
        self.limit = limit
        self.window = window
        self.hits: dict[str, list[float]] = {}

    async def __call__(self, request: Request, call_next):
        key = request.client.host          # 按 IP 限流
        now = time.monotonic()
        records = [t for t in self.hits.get(key, []) if now - t < self.window]

        if len(records) >= self.limit:
            raise HTTPException(status_code=429, detail="请求过于频繁，请稍后再试")

        records.append(now)
        self.hits[key] = records
        return await call_next(request)

app.add_middleware(SimpleRateLimitMiddleware, limit=100, window=60)
```

> 生产环境建议使用 `slowapi`（基于 limits 库）或 Redis 实现，支持分布式与更精细的 Key 策略（IP/用户/接口维度）。

## 三、性能定位

### 3.1 慢接口排查

**定位思路**：性能问题排查遵循「先找入口再找瓶颈」原则——先确认是哪个接口/函数慢，再定位是 I/O 慢还是 CPU 慢。

```
排查流程
① 压测/日志发现慢接口
② 用 cProfile / line_profiler 定位热点函数
③ 区分 I/O 密集（等待外部）还是 CPU 密集（计算）
④ I/O 慢 → 检查超时/重试/连接池/第三方服务
   CPU 慢 → 检查算法/缓存/是否可并行
⑤ 优化后复测，量化提升
```

**cProfile 使用**：

```bash
# 命令行对脚本做性能剖析，输出前 20 个最耗时的调用
python -m cProfile -s cumtime slow_endpoint.py | head -30
```

```python
import cProfile
import pstats
from io import StringIO

def profile_func(func, *args, **kwargs):
    profiler = cProfile.Profile()
    profiler.enable()
    result = func(*args, **kwargs)
    profiler.disable()

    s = StringIO()
    pstats.Stats(profiler, stream=s).sort_stats("cumulative").print_stats(15)
    print(s.getvalue())
    return result
```

**line_profiler 逐行分析**：

```python
# 安装：pip install line-profiler
from line_profiler import LineProfiler

def process_orders(orders):
    total = 0
    for o in orders:          # ← 逐行统计耗时
        total += o["amount"] * 0.99
        total += o.get("bonus", 0)
    return total

lp = LineProfiler()
lp.add_function(process_orders)
lp.enable()
process_orders([{"amount": i, "bonus": i % 2} for i in range(100_000)])
lp.disable()
lp.print_stats()
```

### 3.2 I/O vs CPU 瓶颈

**I/O 密集**：等待网络/磁盘响应占主导。瓶颈特征是「并发低、单请求慢、CPU 空闲」。优化方向是**增加并发 + 缩短等待**。

**CPU 密集**：计算占主导。瓶颈特征是「CPU 打满、吞吐受限」。优化方向是**缓存 + 并行 + 算法优化**。

| 指标 | I/O 瓶颈 | CPU 瓶颈 |
|:-----|:---------|:---------|
| CPU 使用率 | 低 | 接近 100% |
| 平均响应时间 | 高（等待） | 中（计算） |
| 并发数提升 | 吞吐显著上升 | 吞吐几乎不变 |
| 首选优化 | 异步化/连接池/缓存 | 缓存/并行/降复杂度 |

**内存瓶颈**：用 `memory_profiler` 定位内存增长点。

```python
# 安装：pip install memory_profiler
# 装饰器逐行查看内存占用
from memory_profiler import profile

@profile
def load_large_data():
    big_list = [i * 2 for i in range(1_000_000)]
    return sum(big_list)

load_large_data()
```

### 3.3 常见性能反模式

| 反模式 | 问题 | 优化 |
|:-------|:-----|:-----|
| 循环内发起 HTTP/DB 请求 | N+1 次往返 | 批量查询 / 并发 gather |
| 重复计算相同结果 | 浪费 CPU | `lru_cache` / 预计算 |
| 大列表拼接 `+=` | O(n²) | 生成器 / `collections.deque` |
| 同步阻塞调用 | 拖垮事件循环 | 异步化 / 线程池 |
| 无分页全量加载 | 内存爆炸 | 分页 / 流式处理 |
| 字符串循环拼接 | 创建大量中间对象 | `''.join(list)` |

```python
import functools

# ❌ 反模式：循环内重复计算昂贵结果
def bad():
    for i in range(1000):
        result = expensive_calc(i % 10)   # 相同入参重复计算

# ✅ 优化：缓存相同入参的结果
@functools.lru_cache(maxsize=128)
def expensive_calc(x):
    return x * x + 1
```

## 四、locust 性能压测

### 4.1 locust 基础

**locust**：基于 Python 的负载测试工具。核心概念是 `HttpUser`（虚拟用户）与 `task`（任务），模拟真实用户行为。

```bash
# 安装
pip install locust

# 启动（UI 在 http://localhost:8089）
locust -f loadtest.py --host https://api.example.com --headless \
    -u 1000 --spawn-rate 50 -t 5m \
    --html report.html
```

```python
from locust import HttpUser, task, between

class ApiUser(HttpUser):
    """模拟 API 用户：以 0.5~2s 间隔随机执行任务"""

    wait_time = between(0.5, 2)            # 每次任务间的随机等待

    @task(3)                               # 权重：3/5 概率执行
    def get_items(self):
        self.client.get("/api/items?page=1")

    @task(2)
    def get_detail(self):
        self.client.get("/api/items/42")

    @task(1)
    def create_item(self):
        self.client.post(
            "/api/items",
            json={"name": "test", "price": 9.9},
            headers={"Authorization": "Bearer <token>"},
        )
```

### 4.2 压测指标解读

**关键指标**：

| 指标 | 含义 | 参考 |
|:-----|:-----|:-----|
| RPS（Requests/s） | 每秒请求数，反映吞吐 | 越高越好 |
| 响应时间中位数/95%/99% | 延迟分布 | p95 < 500ms 较佳 |
| 失败率 | 请求失败占比 | 压测中 <1% |
| 并发用户数 | 在线虚拟用户 | 与目标容量匹配 |

**容量规划**：压测目标不是「无限高」，而是找到「在可接受延迟下的最大吞吐」。

```
压测曲线示意
吞吐(RPS)
   │           ____
   │      ____/
   │  ___/            ← 达到瓶颈后不再增长
   │ /
   └──────────────────→ 并发数
     ↑ 拐点=最佳容量（再增加只会推高延迟）
```

### 4.3 阶梯压测与结论

**阶梯压测**：逐步增加并发（100→500→1000），观察吞吐与延迟变化，定位系统的「性能拐点」。

```python
from locust import HttpUser, task, constant
import json

class StepUser(HttpUser):
    """配合 --step-load 做阶梯式压测"""

    wait_time = constant(1)

    @task
    def home(self):
        with self.client.get("/", catch_response=True) as resp:
            # 把响应时间写入统计
            if resp.elapsed.total_seconds() > 2:
                resp.failure(f"响应超过 2s: {resp.elapsed.total_seconds():.2f}s")
```

```bash
# 阶梯式压测：每 30s 增加 100 并发，上限 1000
locust -f loadtest.py --host https://api.example.com \
    -u 1000 --spawn-rate 100 --step-load \
    --step-users 100 --step-time 30s \
    --headless -t 10m --html report.html
```

**压测结论输出模板**：

```text
压测报告摘要
────────────
目标接口  : GET /api/items
测试配置  : 最大并发 1000，阶梯每 30s +100，时长 10min
结果      :
  - 峰值吞吐 : 850 RPS（出现在并发 600 时）
  - 最佳容量 : 并发 500（p95=380ms，失败率 0%）
  - 拐点     : 并发 >600 后延迟陡增，p95 破 1.5s
优化建议  :
  1. 命中缓存比例 68% → 提升至 85% 可再涨 30% 吞吐
  2. /api/items 存在 N+1 查询，建议批量预取
```

## 实践项目

### 项目 1：FastAPI 接口限流器

**目标**：实现一个基于 Redis 的分布式限流中间件，支持按 IP 和按用户维度限流。

**步骤**：

1. 用 Redis + Lua 脚本实现令牌桶（原子操作，多 worker 一致）
2. 封装成 FastAPI 中间件，从请求头提取用户维度
3. 支持配置化：不同路由可配不同限流阈值
4. 限流触发时返回 `429` + `Retry-After` 响应头
5. 用 locust 压测验证：超限请求被正确拦截

**目标**：对一个模拟的慢接口做「定位 → 优化 → 复测」全流程，输出量化报告。

**步骤**：
