# 微服务与消息队列

## 一、微服务架构基础

### 1.1 微服务核心概念

微服务是一种将单体应用拆分为一组小型独立服务的架构风格，每个服务围绕业务能力构建，可独立开发、部署和扩展。

**拆分原则**

| 原则 | 说明 | 示例 |
|------|------|------|
| **按业务能力拆分** | 每个服务只负责一个清晰的业务领域 | 用户服务、订单服务、库存服务 |
| **单一职责** | 服务内部高内聚，对外低耦合 | 订单服务只处理订单生命周期 |
| **独立数据库** | 每个服务拥有自己的数据库，避免共享表 | 订单库、用户库分离 |
| **独立部署** | 服务可单独发布、回滚、扩缩容 | 库存服务可独立扩容应对秒杀 |
| **故障隔离** | 单个服务宕机不影响整体系统 | 推荐服务不可用不影响下单 |

**微服务架构核心组件**

```
┌─────────┐      ┌──────────┐      ┌─────────┐
│ 客户端   │ ───→ │  网关     │ ───→ │ 服务注册 │
└─────────┘      │ (Gateway)│      │ (Nacos) │
                 └────┬─────┘      └────┬────┘
                      │                 │
              ┌───────┼───────┐  注册/发现
              ▼       ▼       ▼        │
         ┌──────┐ ┌──────┐ ┌──────┐   │
         │用户服务│ │订单服务│ │库存服务│ ──┘
         └──────┘ └──────┘ └──────┘
```

1. **网关（API Gateway）**：统一入口，负责路由转发、鉴权、限流、负载均衡
2. **注册中心（Registry）**：服务启动时注册，客户端通过它发现可用服务实例
3. **服务间通信**：HTTP/REST、gRPC、消息队列三种方式

### 1.2 服务发现与注册

Python 微服务中常用的服务发现方案：

```python
# 使用 etcd 实现简单服务注册
import etcd3

client = etcd3.client(host='127.0.0.1', port=2379)

# 服务启动时注册（key 带 TTL 自动过期）
def register_service(name: str, host: str, port: int, ttl: int = 30):
    key = f"/services/{name}/{host}:{port}"
    value = f"{host}:{port}"
    client.put(key, value, lease=client.lease(ttl))

# 服务续约（心跳）
def heartbeat(name: str, host: str, port: int, ttl: int = 30):
    key = f"/services/{name}/{host}:{port}"
    lease = client.lease(ttl)
    client.put(key, f"{host}:{port}", lease=lease)
    while True:
        lease.refresh()   # 定期刷新 TTL，模拟心跳
        time.sleep(ttl / 3)

# 客户端发现服务
def discover(name: str) -> list[str]:
    results, _ = client.get_prefix(f"/services/{name}")
    return [r[0].decode() for r in results]
```

**注册中心方案对比**

| 方案 | 一致性 | 特点 | 适用场景 |
|------|--------|------|---------|
| **etcd** | Raft 强一致 | 简单轻量、Go 实现 | 中小型微服务 |
| **Consul** | Raft 强一致 | 内置健康检查、DNS 接口 | 需要多数据中心 |
| **Nacos** | AP + CP 可选 | 服务发现 + 配置管理一体 | Spring 生态或混合架构 |
| **ZooKeeper** | ZAB 强一致 | 生态成熟，运维较重 | 大数据相关场景 |

### 1.3 Python 微服务框架对比

```python
# Nameko 示例：一个微服务即一个 Python 类
from nameko.rpc import rpc

class OrderService:
    name = "order_service"

    @rpc
    def create_order(self, user_id: int, amount: float) -> dict:
        # 业务逻辑：创建订单
        return {"order_id": 1001, "user_id": user_id, "amount": amount}
```

| 框架 | 通信方式 | 异步 | 特点 |
|------|---------|------|------|
| **Nameko** | RPC（RabbitMQ） | ✅ | 类方法即服务，上手快，适合入门 |
| **FastAPI 集群** | HTTP | ✅ | 借助 Uvicorn + 负载均衡，生态最好 |
| **gRPC** | RPC（HTTP/2） | ✅ | 高性能、强类型，跨语言 |
| **Django + DRF** | HTTP | ❌ | 单体偏重，适合成熟业务 |

## 二、gRPC 详解

### 2.1 gRPC 基础概念

gRPC 是 Google 开源的高性能 RPC 框架，基于 **HTTP/2** 协议，使用 **Protocol Buffers（protobuf）** 作为接口定义语言（IDL），默认支持四种调用模式。

**proto 文件定义接口**

```proto
syntax = "proto3";

package order;

// 订单服务接口定义
service OrderService {
  // 一元调用：请求一个，响应一个
  rpc CreateOrder(CreateOrderRequest) returns (OrderResponse);
  // 服务端流式：一次请求，流式返回多个结果
  rpc ListOrders(ListOrdersRequest) returns (stream OrderResponse);
}

message CreateOrderRequest {
  int32 user_id = 1;
  double amount = 2;
  string remark = 3;
}

message OrderResponse {
  int32 order_id = 1;
  int32 user_id = 2;
  double amount = 3;
  string status = 4;
}
```

**生成 Python 代码**

```bash
# 安装 grpcio-tools 后根据 proto 生成代码
pip install grpcio grpcio-tools

# 生成 _pb2.py 和 _pb2_grpc.py
python -m grpc_tools.protoc \
  -I./protos \
  --python_out=./gen \
  --grpc_python_out=./gen \
  ./protos/order.proto
```

### 2.2 gRPC 服务端实现

```python
# server.py — gRPC 服务端
import grpc
import order_pb2
import order_pb2_grpc
from concurrent import futures


class OrderService(order_pb2_grpc.OrderServiceServicer):
    def CreateOrder(self, request, context):
        # 业务处理：创建订单
        return order_pb2.OrderResponse(
            order_id=1001,
            user_id=request.user_id,
            amount=request.amount,
            status="CREATED",
        )


def serve():
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
    order_pb2_grpc.add_OrderServiceServicer_to_server(OrderService(), server)
    server.add_insecure_port("[::]:50051")
    print("gRPC 服务启动在 :50051")
    server.start()
    server.wait_for_termination()


if __name__ == "__main__":
    serve()
```

### 2.3 gRPC 客户端实现

```python
# client.py — gRPC 客户端
import grpc
import order_pb2
import order_pb2_grpc

with grpc.insecure_channel("localhost:50051") as channel:
    stub = order_pb2_grpc.OrderServiceStub(channel)

    # 一元调用
    request = order_pb2.CreateOrderRequest(user_id=42, amount=99.9, remark="测试订单")
    response = stub.CreateOrder(request)
    print(f"订单创建成功: id={response.order_id} status={response.status}")

    # 超时与重试：Deadline 控制
    try:
        response = stub.CreateOrder(request, timeout=5)
    except grpc.RpcError as e:
        if e.code() == grpc.StatusCode.DEADLINE_EXCEEDED:
            print("调用超时，请稍后重试")
```

**gRPC vs REST 对比**

| 对比维度 | gRPC | REST |
|---------|------|------|
| 传输协议 | HTTP/2（多路复用、二进制） | HTTP/1.1（文本） |
| 数据格式 | protobuf（二进制、体积小） | JSON/XML（可读性好） |
| 接口契约 | proto 强类型 | 文档约定，易漂移 |
| 性能 | 高（序列化快、连接复用） | 中 |
| 浏览器支持 | 差（需 grpc-web 网关） | 原生支持 |
| 调试友好度 | 低（需 grpcurl） | 高（curl/Postman） |
| 适用场景 | 内部服务间高性能调用 | 对外 API、前端交互 |

## 三、消息队列

### 3.1 RabbitMQ 详解

RabbitMQ 是一个基于 **AMQP 协议** 的消息中间件，以 Broker 为中心，通过 **Exchange（交换机）** 将消息路由到 **Queue（队列）**。

**核心概念**

1. **Producer（生产者）**：发送消息的应用
2. **Consumer（消费者）**：接收处理消息的应用
3. **Exchange（交换机）**：消息路由中枢，按类型决定分发策略
4. **Queue（队列）**：存储待消费消息
5. **Binding（绑定）**：交换机与队列之间的绑定关系（含路由键）

**Exchange 四种类型**

| 类型 | 路由规则 | 适用场景 |
|------|---------|---------|
| **direct** | 精确匹配 routing_key | 点对点发送 |
| **fanout** | 广播给所有绑定队列 | 日志广播、通知 |
| **topic** | 通配符匹配（`*` 一个词、`#` 任意多个） | 按主题分类 |
| **headers** | 按消息头匹配 | 复杂路由 |

**pika 生产者示例**

```python
import pika

# 建立连接
connection = pika.BlockingConnection(
    pika.ConnectionParameters("localhost", 5672)
)
channel = connection.channel()

# 声明交换机（topic 类型，持久化）
channel.exchange_declare(exchange="order_events", exchange_type="topic", durable=True)

# 声明队列并绑定
channel.queue_declare(queue="order_created", durable=True)
channel.queue_bind(exchange="order_events", queue="order_created", routing_key="order.created")

# 发布消息（持久化投递）
channel.basic_publish(
    exchange="order_events",
    routing_key="order.created",
    body='{"order_id": 1001, "amount": 299.0}',
    properties=pika.BasicProperties(delivery_mode=2),   # 2=消息持久化
)
print("消息已发送")
connection.close()
```

**pika 消费者示例**

```python
import pika, json

def callback(ch, method, properties, body):
    # 收到消息后的业务处理
    data = json.loads(body)
    print(f"处理订单: {data['order_id']}")

    # 手动确认：处理成功才 ACK，失败不 ACK 会重回队列
    ch.basic_ack(delivery_tag=method.delivery_tag)

connection = pika.BlockingConnection(
    pika.ConnectionParameters("localhost", 5672)
)
channel = connection.channel()
channel.queue_declare(queue="order_created", durable=True)

# 公平分发：每次只取一条，处理完再取下一条
channel.basic_qos(prefetch_count=1)
channel.basic_consume(queue="order_created", on_message_callback=callback)
print("开始消费，Ctrl+C 退出")
channel.start_consuming()
```

### 3.2 Kafka 基础

Kafka 是一个**分布式流处理平台**，以 **Partition（分区）** 为单位存储消息，支持高吞吐、持久化、水平扩展。

**核心概念**

1. **Topic（主题）**：消息的逻辑分类
2. **Partition（分区）**：Topic 的物理分片，每个分区内部消息有序
3. **Offset（偏移量）**：分区内消息的顺序编号
4. **Consumer Group（消费者组）**：组内消费者共同消费一个 Topic，分区被均衡分配

**kafka-python 生产者**

```python
from kafka import KafkaProducer
import json

producer = KafkaProducer(
    bootstrap_servers="localhost:9092",
    value_serializer=lambda v: json.dumps(v).encode("utf-8"),
    acks="all",            # 所有副本确认后才返回
    retries=3,             # 发送失败重试
)

# 指定 key 可保证相同 key 进入同一分区（保证顺序）
producer.send("order_events", key=b"1001", value={"order_id": 1001, "amount": 299.0})
producer.flush()
print("消息已发送")
```

**kafka-python 消费者**

```python
from kafka import KafkaConsumer

consumer = KafkaConsumer(
    "order_events",
    bootstrap_servers="localhost:9092",
    group_id="order-service-group",
    auto_offset_reset="earliest",   # 从最早消息开始
    enable_auto_commit=False,       # 手动提交偏移量，避免消息丢失
)

for message in consumer:
    print(f"分区={message.partition} offset={message.offset} 值={message.value}")
    # 业务处理成功后手动提交
    consumer.commit()
```

**RabbitMQ vs Kafka 对比**

| 对比维度 | RabbitMQ | Kafka |
|---------|----------|-------|
| 定位 | 通用消息队列 | 分布式流处理平台 |
| 吞吐量 | 中（万级/秒） | 高（百万级/秒） |
| 消息顺序 | 单队列有序 | 单分区有序 |
| 消息堆积 | 不擅长 | 擅长（磁盘顺序读写） |
| 消费模式 | 推（Push） | 拉（Pull） |
| 适用场景 | 业务解耦、复杂路由 | 日志采集、流式计算、削峰 |

### 3.3 消息可靠性

消息从生产到消费有三个环节，每一环都可能丢失消息：

```
生产者 ──1.发送──→ Broker ──2.存储──→ 消费者
   │                    │                │
   确认机制             持久化            手动 ACK
```

**生产者可靠发送**

```python
# 1. 开启生产者确认（RabbitMQ Publisher Confirm）
import pika

connection = pika.BlockingConnection(
    pika.ConnectionParameters("localhost", 5672)
)
channel = connection.channel()
channel.confirm_delivery()   # 开启 confirm 模式

try:
    channel.basic_publish(
        exchange="order_events",
        routing_key="order.created",
        body=b"hello",
        properties=pika.BasicProperties(delivery_mode=2),
    )
    print("消息已确认到达 Broker")
except pika.exceptions.UnroutableError:
    print("消息路由失败")   # 交换机找不到队列
```

**死信队列（DLQ）**

当消息满足以下条件之一时，会被投递到死信队列：
1. 消息被消费者**拒绝**（basic.reject/basic.nack）且 `requeue=False`
2. 消息 **TTL 过期**
3. 队列达到 **最大长度**

```python
# 声明死信队列并绑定
channel.exchange_declare(exchange="dlx", exchange_type="direct", durable=True)
channel.queue_declare(queue="dead_letter_queue", durable=True)
channel.queue_bind(exchange="dlx", queue="dead_letter_queue", routing_key="dlx")

# 主队列绑定死信交换机，并设置消息 TTL
channel.queue_declare(
    queue="order_queue",
    durable=True,
    arguments={
        "x-dead-letter-exchange": "dlx",        # 死信投递到 dlx 交换机
        "x-dead-letter-routing-key": "dlx",
        "x-message-ttl": 60000,                 # 消息 60 秒未消费视为过期
    },
)

# 消费者主动拒绝，消息进入死信队列
def callback(ch, method, properties, body):
    try:
        process_order(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:
        # 不重试，直接进死信队列，人工排查
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)
```

**消费幂等性**

网络异常可能导致消息被重复投递，消费者必须保证**幂等**：

```python
# 幂等方案 1：唯一键去重（用 Redis）
import redis

r = redis.Redis()

def process_order(order_id: str):
    # set nx：只有键不存在才设置成功，返回 True 表示第一次处理
    if not r.set(f"processed:{order_id}", "1", nx=True, ex=86400):
        print(f"订单 {order_id} 已处理过，跳过")
        return
    # 真正执行业务逻辑
    update_db(order_id)

# 幂等方案 2：数据库唯一索引 + 冲突处理
# CREATE UNIQUE INDEX uk_order ON orders(order_id);
```

## 四、分布式事务与通信选型

### 4.1 分布式事务思路

跨服务的数据一致性无法用单库事务解决，常用方案：

**最终一致性（异步确保）**

```
用户服务                         订单服务
  │  1. 扣减积分                     │
  │ ────2. 发消息(积分变更)──────────→ │
  │  3. 本地事务提交                 │ 4. 本地事务处理积分变更
  │ ←────5. 确认/重试─────────────────│
  └─────────────────────────────────┘
```

**Saga 模式**

将一个大事务拆成多个本地事务，每个本地事务都有**补偿操作**：

```python
# 伪代码：订单-库存 Saga
def create_order_with_stock():
    try:
        order_id = order_service.create_order()      # 步骤1：建订单
        stock_service.deduct_stock(order_id)         # 步骤2：扣库存
        payment_service.pay(order_id)                # 步骤3：支付
    except Exception:
        # 任一步失败，逆序执行补偿
        payment_service.refund(order_id)             # 补偿3：退款
        stock_service.restore_stock(order_id)        # 补偿2：加回库存
        order_service.cancel_order(order_id)         # 补偿1：取消订单
```

**本地消息表**

```
1. 业务操作 + 消息表记录，在同一个数据库事务中提交
2. 后台任务扫描未发送的消息，可靠投递到 MQ
3. 消费者处理成功后回调确认，删除本地消息
```

**分布式事务方案对比**

| 方案 | 一致性 | 复杂度 | 适用场景 |
|------|--------|--------|---------|
| 本地消息表 | 最终一致 | 低 | 对延迟不敏感的业务 |
| Saga 补偿 | 最终一致 | 中 | 长事务、微服务间 |
| TCC（Try-Confirm-Cancel） | 最终一致 | 高 | 高并发、强需求 |
| 2PC/XA | 强一致 | 高 | 极少用，性能差 |

### 4.2 通信模式选型

| 通信模式 | 同步性 | 耦合度 | 适用场景 |
|---------|--------|--------|---------|
| **HTTP/REST** | 同步 | 低 | 对外 API、查询类 |
| **gRPC** | 同步 | 中 | 内部高性能调用 |
| **消息队列** | 异步 | 极低 | 解耦、削峰、事件驱动 |

**选型建议**：

1. 需要实时返回结果 → HTTP/gRPC 同步调用
2. 不关心结果或可异步处理 → 消息队列
3. 内部服务、性能敏感 → gRPC
4. 对外开放 → REST
