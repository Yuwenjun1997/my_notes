# LangGraph 状态图入门

> 上一阶段结尾的思考题：`create_agent` 无法保证"先 A 再 B"的顺序。LangGraph 就是官方给出的答案——**把流程画成一张图，让每一步都可控、可断点、可恢复**。官方定位它叫 **Runtime（运行时）**。

## 一、为什么需要 LangGraph

### 1.1 Agent 的"失控"问题

`create_agent` 是一个**黑盒循环**：模型想调什么工具就调什么，流程顺序不受我们控制。这在"流程必须确定"的场景（先查询订单 → 再执行退款 → 最后发通知）里是致命缺陷——**退款必须先于通知，不能靠模型自觉。**

### 1.2 类比：AutoML 与流程引擎

- `create_agent` 像"一键训练"：省事，但你不能干预过程。
- **LangGraph** 像**状态机 / 工作流引擎**：你把每一步画成节点、连好边，运行时就严格按图走，还能在任意节点暂停、等人确认、再从断点继续。

官方有一个关键说法：**"LangChain agents run on top of LangGraph"**（LangChain 的 Agent 其实是跑在 LangGraph 之上的）。也就是说 LangGraph 更底层、更接近"运行时"，LangChain 的 Agent 只是它的一种简化封装。

## 二、核心概念（官方术语 → 大白话）

| 官方术语 | 大白话 | 类比 |
|:---------|:-------|:-----|
| **State**（状态） | 整个流程共享的"数据袋"，每个节点都能读写 | 流水线上的传单 / 记账本 |
| **Node**（节点） | 流程中的一步（一个函数），接收 State、处理、返回更新 | 流水线上的工位 |
| **Edge**（边） | 从一个节点到另一个节点的连线（默认顺序执行） | 传送带 |
| **Conditional Edge**（条件边） | 根据状态"决定下一步走哪条边"的函数 | 分拣员：看传单内容决定往哪走 |
| **START / END** | 流程的起点和终点 | 流水线的入口和出口 |
| **compile()** | 把图画好后再"编译"成可执行对象 | 把图纸交给施工队 |
| **Checkpointer** | 把每一步状态存下来，可断点续跑（下一节详讲） | 每道工序都拍照存档 |

> 🧠 **一句话记住**：**LangGraph = State（数据） + Node（步骤） + Edge（顺序/条件）。** 你负责画图，运行时负责执行。

## 三、StateGraph 最小示例

### 3.1 定义 State

```python
from typing import TypedDict

class State(TypedDict):
    messages: list[str]      # 流程共享的状态：一个消息列表
    total: int               # 还可以加任意字段
```

> 💡 **含义解释**：State 就是一个 `TypedDict`（带类型标注的字典）。它贯穿整个流程——**每个节点读它、改它，改完返回"要更新的部分"**，LangGraph 自动帮你合并。

### 3.2 定义节点（每个节点就是"流水线的一道工序"）

```python
def step_1(state: State) -> dict:
    """第一步：加一条消息。"""
    return {"messages": state["messages"] + ["已执行：检查订单"]}

def step_2(state: State) -> dict:
    """第二步：加一条消息。"""
    return {"messages": state["messages"] + ["已执行：发起退款"]}

def step_3(state: State) -> dict:
    return {"messages": state["messages"] + ["已执行：发送通知"]}
```

### 3.3 建图、连边、编译

```python
from langgraph.graph import StateGraph, START, END

# 1. 建图（要传入 State 类型）
graph = StateGraph(State)

# 2. 注册节点
graph.add_node("check", step_1)
graph.add_node("refund", step_2)
graph.add_node("notify", step_3)

# 3. 连边：入口 → check → refund → notify → 出口
graph.add_edge(START, "check")
graph.add_edge("check", "refund")
graph.add_edge("refund", "notify")
graph.add_edge("notify", END)

# 4. 编译成可执行对象
app = graph.compile()
```

### 3.4 执行

```python
result = app.invoke({"messages": [], "total": 0})
print(result["messages"])
# ['已执行：检查订单', '已执行：发起退款', '已执行：发送通知']
```

> ✅ 这就是"**保证先 A 再 B**"：`check → refund → notify` 的顺序被边写死了，模型无权改动。**想加一个步骤？加一个节点、连两条边即可。**

## 四、条件分支示例

现实流程常常是"看情况分叉"：订单金额为 0 → 直接结束；大于 0 → 走退款。这就是 **Conditional Edge（条件边）**。

```python
def route_refund(state: State) -> str:
    """分拣员：根据金额决定下一步走到哪个节点。"""
    return "refund" if state["total"] > 0 else "cancel"

graph = StateGraph(State)
graph.add_node("check", step_1)
graph.add_node("refund", step_2)
graph.add_node("cancel", lambda s: {"messages": s["messages"] + ["无需退款"]})
graph.add_node("notify", step_3)

graph.add_edge(START, "check")
graph.add_conditional_edges(
    "check",                       # 从 check 出发
    route_refund,                  # 分拣函数：返回节点名
    {"refund": "refund", "cancel": "cancel"},   # 返回值 → 目标节点
)
graph.add_edge("refund", "notify")
graph.add_edge("cancel", "notify")
graph.add_edge("notify", END)

app = graph.compile()
```

```text
START → check ──(金额>0)──→ refund ──→ notify ──→ END
                └─(金额=0)─→ cancel ──┘
```

> 💡 **含义解释**：`add_conditional_edges` 里的第一个函数是"分拣员"，返回值是一个节点名；后面的字典是"返回值 → 下一节点"的映射。**这就是 LangGraph 让你精确控制流程的地方。**

## 五、LangGraph vs LangChain Agent 对比

| 对比维度 | LangChain `create_agent` | LangGraph `StateGraph` |
|:---------|:-------------------------|:-----------------------|
| 控制力 | 低（黑盒循环） | 高（每个节点/边都可见可控） |
| 分支/循环/并行 | 不支持显式控制 | 原生支持 |
| 持久化 | 无 | Checkpointer 支持断点续跑 |
| 人工审批 | 无 | interrupt 支持（下一节） |
| 学习成本 | 低 | 中 |
| 用在哪 | 单目标简单 Agent | 复杂工作流、需要严格顺序的场景 |

> ⚠️ **官方建议**：能用 `create_agent` 就别用 LangGraph（更省事）；需要**精确控制**才升级。两者不是竞争关系，而是**不同抽象层级**。

## 📝 实践项目

### 目标

用 LangGraph 搭建一个"**有分支 + 有顺序保证**"的处理流程。

### 步骤

1. **定义 State**：`input_text`、`steps_done`、`result` 三个字段。
2. **三个节点**：`clean`（清洗文本）、`analyze`（分析情绪）、`respond`（生成回复）。
3. **条件边**：如果 `input_text` 为空 → 直接跳到 `respond`（返回提示语）；否则按 `clean → analyze → respond` 走。
4. **编译并测试两种情况**：正常输入 / 空输入，观察走了不同的路径。
5. **打印每个节点的中间 State**（可在节点内 `print`），体会"状态贯穿全程"。

> 🧠 **思考题**：上面的流程跑完就结束了。如果进程中途崩溃，或用户希望"暂停，下次继续"，State 还存在吗？—— 答案在下一节：**Checkpointer（检查点）**。
