# LangChain 核心抽象与 RAG

> 这一节认识 LangChain 的"零件库"里都有哪些零件，并亲手搭一条 RAG 管线。理解本节后，你就掌握了后续所有层级的通用语法。

## 一、LangChain 的核心抽象

官方文档把 LangChain 定义为 **Framework（框架）**——它本身不是模型，而是 **模型与工具的"统一接口"**。核心抽象一共四件套：

| 抽象 | 官方术语 | 大白话 | 类比 |
|:-----|:---------|:-------|:-----|
| **模型** | ChatModel / LLM | 大模型接口，输入消息返回文本 | 发动机 |
| **提示词** | PromptTemplate | 把用户输入填进模板，拼出完整指令 | 操作手册 |
| **工具** | Tool | 让模型能调用外部能力的函数 | 外接设备 |
| **检索** | Retriever | 从文档/向量库里找出相关内容 | 资料库检索员 |

> 💡 官方文档说 LangChain 是 **provider-agnostic（与供应商无关）**：同一套代码，换个模型供应商只要换一个类即可，其余不变。

## 二、模型调用（ChatModel）

### 2.1 最基础的用法：`invoke`

```python
from langchain_anthropic import ChatAnthropic

model = ChatAnthropic(model="claude-sonnet-4-5-20250929")

result = model.invoke("用一句话介绍你自己")
print(result.content)          # 模型回复文本
```

### 2.2 消息角色：system / user / assistant

```python
from langchain_core.messages import HumanMessage, SystemMessage

messages = [
    SystemMessage(content="你是一名严谨的 Java 后端专家，只讲事实。"),
    HumanMessage(content="什么是 JVM 垃圾回收？"),
]

result = model.invoke(messages)
print(result.content)
```

> 🧠 **含义解释**：`invoke` 是官方统一的"同步执行"入口（还有 `ainvoke` 异步、`stream` 流式）。**记住 `invoke`，LangChain/LangGraph/Deep Agents 三层的执行接口全叫这个。**

## 三、提示词模板（ChatPromptTemplate）

### 3.1 为什么需要模板

模型输入是文本，但你想让"同一套逻辑"复用于不同输入——这就是**模板**：定义插槽，运行时填值。

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是{domain}领域的专家，回答要简洁。"),
    ("human", "请解释：{question}"),
])

chain = prompt | model                          # LCEL 管道语法
answer = chain.invoke({"domain": "Java", "question": "什么是AOP?"})
print(answer.content)
```

### 3.2 `|` 管道（LCEL）

> **LCEL（LangChain Expression Language，LangChain 表达式语言）**是官方推荐的拼装方式：用 `|` 把"提示词 → 模型 → 输出解析"串成一条管道。它支持流式、并行、批量、日志，是你最常看到的语法。

```text
prompt | model | parser
 输入 →  模板填充 → 模型生成 → 解析成结构化结果
```

```python
from langchain_core.output_parsers import StrOutputParser

chain = prompt | model | StrOutputParser()      # 输出直接是 str，不用 .content
print(chain.invoke({"domain": "Java", "question": "什么是IoC?"}))
```

## 四、工具（Tool）

### 4.1 为什么需要工具

模型只会"生成文字"，不会"查询天气 / 访问数据库 / 执行计算"。**工具 = 一个带描述的函数**，模型会阅读描述，自主决定"该不该调用、怎么调用"。

```python
from langchain.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气，参数 city 为城市名。"""
    # 这里可以调用真实天气 API
    return f"{city} 今天晴天，26℃"

# 使用
result = get_weather.invoke({"city": "北京"})
print(result)          # 北京 今天晴天，26℃
```

> ⚠️ **关键点**：函数上方的 `"""docstring"""` 不是装饰，它就是**工具描述**——模型靠它判断"什么时候该用这个工具"。**描述写得越清楚，模型越会用。**

### 4.2 工具绑定到模型（bind_tools）

```python
model_with_tools = model.bind_tools([get_weather])

# 模型会先输出一个"调用请求"（tool_calls），而不是直接回复
response = model_with_tools.invoke("北京天气怎么样？")
print(response.tool_calls)      # 模型决定：调用 get_weather(city="北京")
```

## 五、RAG：让模型"懂"你的私有资料

### 5.1 RAG 是什么

> **RAG（Retrieval-Augmented Generation，检索增强生成）**：模型不会知道的私有/最新资料，先把它"喂"进向量库；用户提问时，先**检索**出相关内容，再把"资料 + 问题"一起交给模型生成答案。

**为什么要 RAG？** 因为模型的知识有截止日期、且不含私有内容。RAG = **给模型外挂一个可检索的资料库**，比重新训练模型便宜得多、也快得多。

### 5.2 官方 RAG 管线（五步）

```text
加载 → 切分 → 向量化 → 存储/索引 → 检索 + 生成
Load → Split → Embed  → Store      → Retrieve + Generate
```

| 步骤 | 官方组件 | 作用 |
|:-----|:---------|:-----|
| 1 加载 | `DocumentLoader` | 从 PDF/网页/数据库读入文档 |
| 2 切分 | `RecursiveCharacterTextSplitter` | 把长文档切成小块（chunk），避免超长、提升检索精度 |
| 3 向量化 | `Embeddings` | 把每块文本变成一组数字（向量），语义相近的向量距离近 |
| 4 存储 | 向量库（如 Chroma） | 把向量索引存起来，供快速相似度检索 |
| 5 检索+生成 | `Retriever` + 提示词 | 按问题检索相关块，拼进提示词交给模型 |

### 5.3 最小可运行示例

```python
from langchain_chroma import Chroma
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate

# 1. 原始文本（真实项目里来自 DocumentLoader）
docs = ["Claude 是 Anthropic 的大模型。", "Java 17 是 LTS 版本。"]

# 2. 切分
splitter = RecursiveCharacterTextSplitter(chunk_size=50, chunk_overlap=10)
chunks = splitter.create_documents(docs)

# 3+4. 向量化并存入 Chroma（embedding 模型按你的供应商选）
from langchain_anthropic import ChatAnthropic  # 占位，embedding 也可来自官方配套包
from langchain_chroma import Chroma
# vectorstore = Chroma.from_documents(documents=chunks, embedding=embedding)

# 5. 检索器：把"与问题最相关"的块取出来
# retriever = vectorstore.as_retriever()

# 生成模板：资料 + 问题 → 模型
prompt = ChatPromptTemplate.from_messages([
    ("system", "仅根据以下资料回答，资料没有的就说不知道。\n\n资料：\n{context}"),
    ("human", "问题：{question}"),
])

# chain = (retriever | 拼接 context | prompt | model | StrOutputParser())
```

> 💡 上面第 3/4 步的 `embedding` 需要按你的模型供应商配置（如 `langchain-anthropic` / `langchain-openai` 的 Embeddings 类），完整代码见官方 `RAG quickstart`。**核心思想是：检索出来的"上下文块"会被拼进 system 提示词，让模型"先看资料再回答"。**

### 5.4 RAG 和 Agent 的区别（表格）

| 对比维度 | RAG 管线 | Agent |
|:---------|:---------|:-------|
| 形态 | 固定的"检索→生成"直线 | 循环的"思考→行动→观察" |
| 是否自主调用工具 | 否（检索是写死的） | 是（模型自主决定调哪个工具） |
| 典型场景 | 私有资料问答 | 需要多步推理、调用外部系统的任务 |

## 📝 实践项目

### 目标

实现一个能回答"私有文档内容"的 RAG 问答，并给模型加一个自定义工具。

### 步骤

1. **准备几段私有文本**（比如你自己的学习笔记）存成 `notes.txt`。
2. **用 `TextLoader` 加载 → 切分 → 向量化 → 存入 Chroma**（参照官方 RAG quickstart）。
3. **用 `as_retriever()` 拿到检索器**，搭 `retriever → 提示词 → model → 解析器` 管道。
4. **提问**：问一个只在笔记里出现、模型本身不知道的问题，验证它"基于资料回答"。
5. **再写一个 `@tool` 计算函数**（如 `add(a, b)`），用 `bind_tools` 绑定，观察模型是否自主输出 `tool_calls`。

> 🧠 **思考题**：RAG 检索出的上下文会占用模型上下文窗口。如果资料非常多，应该怎么控制每次检索返回的块数量？（提示：`as_retriever(search_kwargs={"k": N})`）
