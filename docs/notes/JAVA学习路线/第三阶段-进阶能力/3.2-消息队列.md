# 消息队列

## 一、消息队列核心概念

### 1.1 为什么需要消息队列

消息队列（Message Queue）是一种中间件技术，用于实现**异步通信**、**削峰填谷**和**系统解耦**。

**核心作用**

| 作用 | 说明 | 类比 |
|------|------|------|
| **异步处理** | 非紧急操作异步执行，提升响应速度 | 餐厅点餐后叫号，不等菜做好 |
| **削峰填谷** | 缓冲突发流量，保护下游系统 | 水库蓄水，错峰放水 |
| **系统解耦** | 生产者和消费者独立演进 | 插头和插座标准统一，互不影响 |
| **最终一致性** | 分布式系统的数据最终一致 | 银行转账分步完成，最终到账 |

**不使用消息队列的问题**

```text
用户下单
    ↓
同步调用：扣库存 → 生成订单 → 发短信 → 送积分 → 更新统计
    ↓
用户等待 2 秒钟 → 体验差
任一环节故障 → 整个流程失败
流量暴增 → 所有系统被打垮
```

**使用消息队列后**

```text
用户下单 → 返回"下单成功"
              ↓
        发送消息到队列
              ↓
      ┌──────┼──────┐
      ↓      ↓      ↓
    扣库存  发短信  送积分
    (异步)  (异步)  (异步)
```

### 1.2 消息模型

**点对点模型（P2P）**

```text
生产者 → 队列 → 消费者（1个）
          ↑
       消息被消费后删除
   一条消息只能被一个消费者消费
```

**发布订阅模型（Pub/Sub）**

```text
生产者 → Topic（主题）
          ↓
    ┌─────┼─────┐
    ↓     ↓     ↓
 消费者1 消费者2 消费者3
    ↑
 每个消费者独立消费消息
 一条消息可以被多个消费者订阅
```

## 二、RabbitMQ

### 2.1 核心概念

```text
Producer（生产者）
    ↓
Exchange（交换机）—— 核心路由组件
    ↓     绑定（Binding）
Queue（队列）
    ↓
Consumer（消费者）
```

**RabbitMQ 核心组件**

| 组件 | 说明 | 类比 |
|------|------|------|
| Producer | 发送消息的应用程序 | 发件人 |
| Exchange | 接收并路由消息到队列 | 邮局分拣中心 |
| Queue | 存储消息的内存/磁盘缓冲区 | 邮箱 |
| Binding | 定义 Exchange 和 Queue 的关系 | 投递规则 |
| Consumer | 接收消息的应用程序 | 收件人 |
| Virtual Host | 隔离资源，不同 vhost 的 Exchange/Queue 互不干扰 | 小区 |
| Channel | 复用 TCP 连接的轻量连接 | 快递员 |

### 2.2 Exchange 类型

**1. Direct Exchange（直连交换机）**

根据 routingKey 精确匹配，将消息路由到绑定相同 key 的队列。

```text
        Direct Exchange
              |
     ┌────────┼────────┐
     | routingKey=error  | routingKey=info
     ↓                    ↓
  Queue(error)          Queue(info)
     ↓                    ↓
  日志消费者            日志消费者

// 使用场景：日志分级处理
// error 级别 → 发送告警
// info 级别 → 记录日志
```

**2. Fanout Exchange（扇出交换机）**

将消息广播到所有绑定的队列，忽略 routingKey。

```text
      Fanout Exchange
              |
     ┌────────┼────────┐
     ↓        ↓        ↓
  Queue-A   Queue-B   Queue-C
     ↓        ↓        ↓
   订单服务  短信服务  邮件服务

// 使用场景：用户注册成功后，同时发送通知邮件、短信、内部通知
```

**3. Topic Exchange（主题交换机）**

根据 routingKey 模式匹配（通配符：`*` 匹配一个单词，`#` 匹配 0 或多个单词）。

```text
       Topic Exchange
              |
   ┌──────────┼──────────┐
   | *.order.#           | order.*
   ↓                      ↓
 Queue(订单处理)        Queue(订单状态变更)
   ↓                      ↓
  物流服务              实时推送

routingKey 示例：
"order.created"      → 匹配 *.order.# 和 order.*
"order.paid"         → 匹配 *.order.# 和 order.*
"order.paid.sms"     → 匹配 *.order.#（不匹配 order.*）
```

**4. Headers Exchange（头部交换机）**

根据消息头属性匹配，忽略 routingKey（很少使用）。

### 2.3 消息可靠性

RabbitMQ 提供了从生产到消费的全链路可靠性保障：

```text
生产者 → Exchange → Queue → 消费者
   ↓          ↓        ↓       ↓
 Confirm   Mandatory  持久化  手动 ACK
```

**1. 生产者确认（Publisher Confirm）**

```java
// application.yml
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # 启用发布者确认
    publisher-returns: true               # 启用路由失败返回

@Configuration
public class RabbitMQConfig {

    @Bean
    public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);

        // 消息路由失败时的回调
        template.setMandatory(true);
        template.setReturnsCallback(returned -> {
            log.error("消息路由失败: exchange={}, routingKey={}, replyCode={}, replyText={}",
                    returned.getExchange(), returned.getRoutingKey(),
                    returned.getReplyCode(), returned.getReplyText());
        });

        // 发布确认回调（消息到达 Exchange）
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (ack) {
                log.debug("消息发送成功: {}", correlationData.getId());
            } else {
                log.error("消息发送失败: {}, cause={}", correlationData.getId(), cause);
                // 重试或记录日志
            }
        });

        return template;
    }
}

// 生产者发送消息
@Service
public class OrderProducer {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    public void sendOrderMessage(Order order) {
        CorrelationData correlationData = new CorrelationData(UUID.randomUUID().toString());

        rabbitTemplate.convertAndSend(
                "order.exchange",
                "order.created",
                order,
                message -> {
                    // 消息持久化
                    message.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                    return message;
                },
                correlationData
        );
    }
}
```

**2. 消费者手动确认（Manual ACK）**

```java
@Component
public class OrderConsumer {

    @RabbitListener(queues = "order.queue")
    public void processOrder(Order order, Channel channel,
                              @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) {
        try {
            // 业务处理
            processOrder(order);

            // 手动确认消息（处理成功后）
            channel.basicAck(deliveryTag, false);
            log.info("订单处理成功: {}", order.getId());

        } catch (Exception e) {
            log.error("订单处理失败: {}", order.getId(), e);

            // 消息重试或死信处理
            // requeue=true：重新入队（重试）
            // requeue=false：丢弃或进入死信队列
            channel.basicNack(deliveryTag, false, false);
        }
    }
}
```

**3. 死信队列（DLQ）**

当消息出现以下情况时，可以进入死信队列：
- 消费者 basicNack 且 requeue=false
- 消息过期（TTL 到期）
- 队列达到最大长度

```java
@Configuration
public class DeadLetterConfig {

    // 正常队列（设置死信交换机和死信路由键）
    @Bean
    public Queue orderQueue() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-dead-letter-exchange", "order.dlx.exchange");     // 死信交换机
        args.put("x-dead-letter-routing-key", "order.dead");           // 死信路由键
        args.put("x-message-ttl", 60000);                               // 消息 TTL（60 秒）
        args.put("x-max-length", 1000);                                 // 队列最大长度
        return new Queue("order.queue", true, false, false, args);
    }

    // 死信交换机
    @Bean
    public DirectExchange deadLetterExchange() {
        return new DirectExchange("order.dlx.exchange");
    }

    // 死信队列
    @Bean
    public Queue deadLetterQueue() {
        return new Queue("order.dlx.queue", true);
    }

    // 绑定死信队列
    @Bean
    public Binding deadLetterBinding() {
        return BindingBuilder.bind(deadLetterQueue())
                .to(deadLetterExchange())
                .with("order.dead");
    }

    // 死信队列消费者（分析和告警）
    @RabbitListener(queues = "order.dlx.queue")
    public void processDeadLetter(Order order) {
        log.error("收到死信消息: 订单ID={}, 超时时间={}", order.getId(), order.getCreatedAt());
        // 告警通知
        alertService.sendAlert("订单处理异常，请检查: " + order.getId());
    }
}
```

### 2.4 消费者组

RabbitMQ 通过**竞争消费模式**实现消费者组：

```text
        消息队列
            |
    ┌───────┼───────┐
    ↓       ↓       ↓
 消费者1  消费者2  消费者3
 （接收不同消息，负载均衡）
```

```java
@Component
public class OrderConsumer {

    // @RabbitListener 创建的消费者属于同一个消费者组
    // 多个实例时，消息会被负载均衡到其中一个
    @RabbitListener(queues = "order.queue", concurrency = "3-5")
    public void handleOrder(Order order) {
        // concurrency = "3-5"：最小 3 个消费者线程，最大 5 个
        log.info("消费者 {} 处理订单: {}", Thread.currentThread().getName(), order.getId());
        orderService.process(order);
    }
}
```

## 三、Kafka

### 3.1 核心概念

```text
Producer → Topic（主题）
              |
        ┌─────┴─────┐
        | Partition 0 | Partition 1 | Partition 2 |
        └─────┬─────┘
              |
     Consumer Group
     ┌────┴────┐
   Consumer1  Consumer2
```

**核心组件**

| 组件 | 说明 |
|------|------|
| Broker | Kafka 服务器节点，一个集群由多个 Broker 组成 |
| Topic | 消息主题（逻辑分类） |
| Partition | 分区（物理分片，有序的日志文件） |
| Offset | 消息在分区内的偏移量（唯一标识） |
| Consumer Group | 消费者组（组内负载均衡消费） |
| Producer | 生产者（发送消息到 Topic） |
| Zookeeper / KRaft | 元数据管理、集群协调（新版本用 KRaft 替代 ZK） |

### 3.2 分区（Partition）和副本（Replica）

**分区机制**

```text
Topic: orders
    ↓
分区 0 (leader)    分区 1 (leader)    分区 2 (leader)
    ↓                    ↓                    ↓
分区 0 (follower)  分区 1 (follower)  分区 2 (follower)
    ↓                    ↓                    ↓
分区 0 (follower)  分区 1 (follower)  分区 2 (follower)
     ↑
  跨 Broker 分布，保证高可用

消息 → key = orderId.hashCode() % 分区数 → 写入指定分区
```

**分区的作用**：提升吞吐量（并行读写）

```java
// 指定分区发送
@Service
public class OrderProducer {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    // 1. 指定分区
    public void sendToPartition(Order order, int partition) {
        ProducerRecord<String, String> record = new ProducerRecord<>(
                "orders", partition, order.getId().toString(), JSON.toJSONString(order));
        kafkaTemplate.send(record);
    }

    // 2. Key 哈希路由（相同 key 的消息进入同一分区，保证顺序）
    public void sendWithKey(Order order) {
        // 相同 orderId 的消息始终进入同一分区（保证顺序）
        kafkaTemplate.send("orders", order.getId().toString(), JSON.toJSONString(order));
    }

    // 3. 默认轮询
    public void send(Order order) {
        kafkaTemplate.send("orders", JSON.toJSONString(order));
    }
}
```

### 3.3 消费者组

消费者组是实现**水平扩展**和**故障容错**的核心机制。

```text
一个分区的消息只能被同一个消费者组中的一个消费者消费

Topic: orders (3 个分区)

场景 A：3 个消费者，3 个分区
  分区0 → 消费者1   分区1 → 消费者2   分区2 → 消费者3
  ✓ 完美对应，每个消费者处理一个分区

场景 B：2 个消费者，3 个分区
  分区0 → 消费者1   分区1 → 消费者2   分区2 → 消费者2
  ✓ 一个消费者可以消费多个分区

场景 C：4 个消费者，3 个分区
  分区0 → 消费者1   分区1 → 消费者2   分区2 → 消费者3
  消费者4 闲置
  ⚠ 消费者数不要超过分区数
```

**配置消费者组**

```java
@Component
public class OrderConsumer {

    @KafkaListener(
            topics = "orders",
            groupId = "order-group",       // 消费者组
            concurrency = "3"               // 消费者线程数（建议 ≤ 分区数）
    )
    public void consume(String message,
                        @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                        @Header(KafkaHeaders.OFFSET) long offset) {
        log.info("分区={}, 偏移量={}, 消息={}", partition, offset, message);
        // 业务处理
        Order order = JSON.parseObject(message, Order.class);
        orderService.process(order);
    }
}
```

### 3.4 消息顺序性

**Kafka 只能在分区内保证顺序**，跨分区无法保证全局顺序。

**保证分区内顺序的条件**

```java
@Service
public class OrderService {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    public void processOrderFlow(Order order) {
        // 相同订单 ID 进入同一分区 → 保证顺序处理
        String key = order.getId().toString();

        // 阶段 1：创建订单
        kafkaTemplate.send("order-flow", key, "CREATE:" + JSON.toJSONString(order));

        // 阶段 2：支付
        kafkaTemplate.send("order-flow", key, "PAY:" + JSON.toJSONString(order));

        // 阶段 3：发货
        kafkaTemplate.send("order-flow", key, "SHIP:" + JSON.toJSONString(order));
    }
}
```

**场景说明**

```text
场景 A：关键 Key 分区（顺序保证 ✓）
  key=order_001 → Partition 0 → CREATE → PAY → SHIP（顺序消费）
  key=order_002 → Partition 1 → CREATE → PAY → SHIP（顺序消费）

场景 B：全局顺序（需要 1 个分区，牺牲吞吐量）
  所有消息 → Partition 0 → 串行消费 ✓
  但是吞吐量受限于单个分区！

场景 C：需要严格全局顺序但不是日志场景
  ❌ 考虑使用单分区 Kafka 或换用 RabbitMQ/RocketMQ
```

### 3.5 Kafka vs RabbitMQ 对比

| 对比维度 | RabbitMQ | Kafka |
|---------|----------|-------|
| **定位** | 消息队列 | 分布式流处理平台 |
| **协议** | AMQP | 自定义 TCP 协议 |
| **吞吐量** | 万级/秒 | 百万级/秒 |
| **延迟** | 微秒级 | 毫秒级 |
| **消息存储** | 消费后删除 | 基于时间/大小策略保留 |
| **消息顺序** | 单队列有序 | 分区内有序 |
| **消息回溯** | 不支持 | 支持（基于 Offset） |
| **路由能力** | 丰富（多种 Exchange） | 弱（基于 Topic） |
| **事务支持** | 完善 | 有限 |
| **运维复杂度** | 中 | 高 |
| **适用场景** | 企业应用、事务性消息 | 日志收集、大数据、流处理 |

**选型建议**

| 场景 | 推荐 |
|------|------|
| 任务队列、异步处理 | RabbitMQ |
| 需要复杂路由 | RabbitMQ（Topic/Direct 灵活） |
| 日志收集和聚合 | Kafka |
| 大数据流处理 | Kafka |
| 消息可靠性要求极高 | RabbitMQ（Confirm + ACK） |
| 海量消息、高吞吐 | Kafka |
| 需要消息回溯 | Kafka |
| 简单易上手 | RabbitMQ |

## 四、实践项目

### 项目 1：RabbitMQ 订单处理系统

**目标**：使用 RabbitMQ 实现订单的异步处理。

**功能要求**：
1. 用户下单后发送消息到队列
2. 订单服务、短信服务、积分服务各自消费消息
3. 使用 Confirm 机制保障消息可靠投递
4. 使用死信队列处理异常订单
5. 使用 Direct Exchange 和 Topic Exchange

**消息流程**：
```text
下单 → Direct Exchange
        ↓
    [order.created] → 订单服务（创建订单）
                     → 库存服务（扣减库存）
    [order.paid]    → 订单服务（更新状态）
                     → 物流服务（生成运单）
```

### 项目 2：Kafka 日志收集系统

**目标**：使用 Kafka 收集和聚合应用日志。

**功能要求**：
1. 多个微服务发送日志到 Kafka
2. 日志按级别分区（ERROR/INFO/DEBUG）
3. 使用不同消费者组处理日志（实时告警组、数据归档组）
4. 支持消息回溯查看历史日志
5. 配合 ELK 实现日志可视化

**消息流程**：
```text
服务A → 发送日志
服务B → 发送日志          → Kafka（Topic: app-logs）
服务C → 发送日志              ↓
                         告警组 → 实时告警
                         归档组 → Elasticsearch
