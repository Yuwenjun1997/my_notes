# 数据库进阶

## 一、MySQL 调优

### 1.1 索引优化

**索引选择原则**

```sql
-- 1. 查看表结构和索引
SHOW CREATE TABLE users;
SHOW INDEX FROM users;

-- 2. 分析查询执行计划
EXPLAIN SELECT * FROM users WHERE name = '张三' AND status = 'ACTIVE';
```

**EXPLAIN 输出详解**

| 列名 | 说明 | 优化目标 |
|------|------|---------|
| id | SELECT 标识符，id 越大越先执行 | - |
| select_type | 查询类型（SIMPLE/PRIMARY/SUBQUERY） | 尽量 SIMPLE |
| table | 表名 | - |
| partitions | 匹配的分区 | - |
| **type** | **访问类型**（从好到差排序↓） | **至少 range，最好 ref/const** |
| possible_keys | 可能使用的索引 | - |
| **key** | **实际使用的索引** | **尽量不为 NULL** |
| key_len | 使用的索引长度（越小越好） | 短键优先 |
| ref | 索引匹配的列 | - |
| **rows** | **扫描行数估算** | **越少越好** |
| filtered | 过滤后剩余百分比 | 越高越好 |
| **Extra** | **附加信息** | **看下面详解** |

**type 字段（访问类型从优到差）**

```text
system > const > eq_ref > ref > range > index > ALL
```

```sql
-- const：主键或唯一索引等值查询（最优）
EXPLAIN SELECT * FROM users WHERE id = 1;           -- type: const

-- eq_ref：JOIN 时使用主键或唯一索引
EXPLAIN SELECT * FROM orders o JOIN users u ON o.user_id = u.id;  -- type: eq_ref

-- ref：普通索引等值查询
EXPLAIN SELECT * FROM users WHERE name = '张三';     -- type: ref（有 name 索引）

-- range：索引范围查询
EXPLAIN SELECT * FROM users WHERE id > 1000;         -- type: range
EXPLAIN SELECT * FROM users WHERE name LIKE '张%';   -- type: range

-- index：全索引扫描（比全表扫描好一点）
EXPLAIN SELECT COUNT(*) FROM users;                  -- type: index

-- ALL：全表扫描（最差，需要优化）
EXPLAIN SELECT * FROM users WHERE status = 'ACTIVE'; -- type: ALL（status 无索引）
```

**Extra 字段需要关注的值**

```sql
-- Using where：使用了 WHERE 条件过滤（正常）
EXPLAIN SELECT * FROM users WHERE name = '张三';

-- Using index：覆盖索引（不需要回表，非常好！）
EXPLAIN SELECT id, name FROM users WHERE name = '张三';
-- 如果 name 上有索引，且只查询 id 和 name，索引中就有这些数据

-- Using index condition：索引下推（ICP，MySQL 5.6+ 好特性）
EXPLAIN SELECT * FROM users WHERE name LIKE '张%' AND age > 20;
-- 在索引遍历时同时过滤 age 条件，减少回表次数

-- Using filesort：需要文件排序（需要优化）
EXPLAIN SELECT * FROM users ORDER BY create_time;
-- 解决：给排序字段加索引

-- Using temporary：使用了临时表（需要优化）
EXPLAIN SELECT status, COUNT(*) FROM users GROUP BY status;
-- 解决：给 GROUP BY 字段加索引
```

**实战优化案例**

```sql
-- 案例 1：分页优化（避免深度分页）
-- ❌ 慢查询（偏移量大时）
SELECT * FROM users ORDER BY id LIMIT 100000, 20;

-- ✅ 优化方案 1：子查询优化（利用索引覆盖）
SELECT * FROM users
WHERE id > (SELECT id FROM users ORDER BY id LIMIT 100000, 1)
ORDER BY id LIMIT 20;

-- ✅ 优化方案 2：记录上次位置（推荐，游标分页）
SELECT * FROM users WHERE id > 100000 ORDER BY id LIMIT 20;

-- 案例 2：ORDER BY 优化
-- ❌ 索引失效
SELECT * FROM users WHERE name = '张三' ORDER BY create_time;

-- ✅ 建立联合索引（name, create_time）
CREATE INDEX idx_name_create_time ON users(name, create_time);

-- 案例 3：GROUP BY 优化
-- ❌ Using temporary
SELECT DATE(create_time), COUNT(*) FROM users GROUP BY DATE(create_time);

-- ✅ 使用冗余字段（建立虚拟列 + 索引）
ALTER TABLE users ADD COLUMN create_date DATE
    GENERATED ALWAYS AS (DATE(create_time)) STORED;
CREATE INDEX idx_create_date ON users(create_date);

SELECT create_date, COUNT(*) FROM users GROUP BY create_date;
```

**索引监控**

```sql
-- 查看索引使用情况
SELECT * FROM sys.schema_unused_indexes;       -- 从未使用的索引（考虑删除）

-- 查看索引统计
SELECT * FROM information_schema.STATISTICS
WHERE table_schema = 'mydb' AND table_name = 'users';

-- 查看索引基数（区分度）
SHOW INDEX FROM users;
-- Cardinality 列：索引的基数（越大越好，接近行数表示区分度高）
```

**SQL 优化常见技巧**

```sql
-- 1. SELECT 指定字段，避免 SELECT *
-- ❌ 不推荐
SELECT * FROM users WHERE name = '张三';

-- ✅ 推荐（只取需要的字段，可以利用覆盖索引）
SELECT id, name, email FROM users WHERE name = '张三';

-- 2. 拆分复杂查询
-- ❌ 一条 SQL 做太多事
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000)
  AND EXISTS (SELECT 1 FROM user_logs WHERE user_id = users.id);

-- ✅ 拆分为多条查询（更容易优化）
SELECT user_id FROM orders WHERE amount > 1000; -- 结果集小
SELECT * FROM users WHERE id IN (...);

-- 3. 用 UNION ALL 代替 OR
-- ❌ OR 可能索引失效
SELECT * FROM users WHERE name = '张三' OR email = 'zhangsan@e.com';

-- ✅ UNION ALL
SELECT * FROM users WHERE name = '张三'
UNION ALL
SELECT * FROM users WHERE email = 'zhangsan@e.com';

-- 4. 批量操作时使用批量 SQL
-- ❌ 逐条插入（N 次网络往返）
INSERT INTO users(name) VALUES('A');
INSERT INTO users(name) VALUES('B');

-- ✅ 批量插入（1 次网络往返）
INSERT INTO users(name) VALUES('A'),('B'),('C');

-- 5. LIMIT 优化：估算行数
-- ✅ 使用 EXPLAIN 估算
EXPLAIN SELECT COUNT(*) FROM users WHERE status = 'ACTIVE';

-- ✅ 精确计数（InnoDB 需要扫描索引，建议用近似值或缓存）
SELECT COUNT(*) FROM users;  -- 千万级会很慢

-- 6. JOIN 优化：小表驱动大表
-- 假设 users 1000 行，orders 100000 行
-- ✅ users 驱动 orders（小表驱动大表）
SELECT * FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE u.status = 'ACTIVE';

-- 7. 避免在 WHERE 中使用函数
-- ❌ 索引失效
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-15';

-- ✅ 索引有效
SELECT * FROM orders
WHERE create_time >= '2024-01-15 00:00:00'
  AND create_time < '2024-01-16 00:00:00';
```

**表设计优化**

```sql
-- 1. 选择合适的数据类型
-- ❌ 浪费空间
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT,          -- 不需要那么大的主键
    status VARCHAR(10) DEFAULT '0',    -- 用 INT 或 ENUM 更好
    name VARCHAR(255),                 -- 过长
    memo TEXT,                         -- 能用 VARCHAR 不用 TEXT
    created_at DATETIME(6)             -- 不需要微秒精度
);

-- ✅ 合理设计
CREATE TABLE users (
    id INT UNSIGNED AUTO_INCREMENT,          -- 够用
    status TINYINT UNSIGNED DEFAULT 0,       -- 0/1 足够
    name VARCHAR(50) NOT NULL,               -- 合理长度
    memo VARCHAR(500),                       -- 短文本用 VARCHAR
    created_at DATETIME                      -- 默认精度
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 2. 使用 NOT NULL（可优化索引性能）
ALTER TABLE users MODIFY name VARCHAR(50) NOT NULL DEFAULT '';

-- 3. 选择合适的表引擎
-- ✅ 大部分场景用 InnoDB（支持事务、行锁）
-- 只读或日志表可用 MyISAM（表锁，但 COUNT(*) 快）

-- 4. 字段冗余设计（空间换时间）
-- ❌ 每次查询都要 JOIN
SELECT o.*, u.name AS user_name
FROM orders o JOIN users u ON o.user_id = u.id;

-- ✅ 适当冗余（减少 JOIN）
ALTER TABLE orders ADD COLUMN user_name VARCHAR(50);
```

## 二、分库分表

### 2.1 为什么要分库分表

**单库瓶颈**

```text
数据量达到一定规模后：
- 单表数据量 > 500 万行：查询性能开始下降
- 单表数据量 > 1 亿行：索引层级变深，B+ 树 3-4 层 → 4-5 层
- 单库连接数有限：无法水平扩展
- 单库写入吞吐量有限：受磁盘 IO 限制
```

**分库分表类型**

```text
垂直分库：按业务拆分到不同数据库
  [订单库]    [用户库]    [商品库]

垂直分表：将宽表拆分为多张窄表
  [user_base(id, name, pwd)] ← 常用字段
  [user_ext(id, avatar, bio)] ← 不常用字段

水平分库：将数据分到多个数据库
  [db_0.users]  [db_1.users]  [db_2.users]
   user_id%3=0   user_id%3=1   user_id%3=2

水平分表：将数据分到同一数据库的多张表
  [users_0]  [users_1]  [users_2]
   user_id%3=0  user_id%3=1  user_id%3=2
```

**分片策略对比**

| 分片策略 | 说明 | 优点 | 缺点 |
|---------|------|------|------|
| 取模分片 | `id % 分片数` | 数据均匀分布 | 扩缩容需要迁移大量数据 |
| 范围分片 | `id 在 [1-1000] → 库1` | 扩容简单 | 可能数据倾斜 |
| 哈希分片 | `hash(key) % 分片数` | 分布均匀 | 扩缩容同样需要迁移 |
| 时间分片 | 按月/日分表 | 按时间归档简单 | 热点数据集中 |
| 一致性哈希 | 虚拟节点哈希环 | 扩缩容影响小 | 实现复杂 |

### 2.2 ShardingSphere 实现

Apache ShardingSphere 是一套开源的分布式数据库中间件。

**核心概念**

```text
应用 → ShardingSphere-JDBC（嵌入应用内，推荐）
  或
应用 → ShardingSphere-Proxy（独立服务，类似数据库代理）
```

**ShardingSphere-JDBC 配置（推荐）**

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.0</version>
</dependency>
```

```yaml
# application.yml
spring:
  shardingsphere:
    # 数据源配置
    datasource:
      names: ds0, ds1               # 两个数据库实例
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.10:3306/db0?useSSL=false
        username: root
        password: root123
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://192.168.1.11:3306/db1?useSSL=false
        username: root
        password: root123

    rules:
      # 分片规则
      sharding:
        tables:
          # 订单表分片配置
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..1}  # 2库 × 2表
            database-strategy:           # 分库策略
              standard:
                sharding-column: user_id
                sharding-algorithm-name: database-inline
            table-strategy:              # 分表策略
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
            key-generate-strategy:       # 分布式主键生成
              column: id
              key-generator-name: snowflake
          # 用户表分片（只分库不分表）
          t_user:
            actual-data-nodes: ds$->{0..1}.t_user
            database-strategy:
              standard:
                sharding-column: id
                sharding-algorithm-name: database-inline

        # 分片算法
        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}   # user_id 取模路由到不同库
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 2}  # order_id 取模路由到不同表

        # 分布式主键算法
        key-generators:
          snowflake:
            type: SNOWFLAKE
            props:
              worker-id: 1
```

**Java API 配置方式**

```java
@Configuration
public class ShardingConfig {

    @Bean
    public DataSource shardingDataSource() throws SQLException {
        // 1. 配置数据源
        Map<String, DataSource> dataSourceMap = new HashMap<>();
        dataSourceMap.put("ds0", createDataSource("jdbc:mysql://192.168.1.10:3306/db0"));
        dataSourceMap.put("ds1", createDataSource("jdbc:mysql://192.168.1.11:3306/db1"));

        // 2. 配置分片规则
        ShardingRuleConfiguration ruleConfig = new ShardingRuleConfiguration();

        // 订单表规则
        ShardingTableRuleConfiguration orderRule = new ShardingTableRuleConfiguration("t_order",
                "ds${0..1}.t_order_${0..1}");  // 2库 × 2表

        // 分库策略：user_id % 2
        orderRule.setDatabaseShardingStrategy(new StandardShardingStrategyConfiguration(
                "user_id", "databaseInlineShardingAlgorithm"));

        // 分表策略：order_id % 2
        orderRule.setTableShardingStrategy(new StandardShardingStrategyConfiguration(
                "order_id", "tableInlineShardingAlgorithm"));

        // 分布式主键
        orderRule.setKeyGenerateStrategy(new KeyGenerateStrategyConfiguration("id", "snowflake"));

        ruleConfig.getTables().add(orderRule);

        // 设置默认分库策略（未配置分片的表路由到 ds0）
        ruleConfig.setDefaultDatabaseShardingStrategy(
                new StandardShardingStrategyConfiguration("id", "databaseInlineShardingAlgorithm"));

        // 3. 创建 ShardingSphere 数据源
        return ShardingSphereDataSourceFactory.createDataSource(
                dataSourceMap, Collections.singleton(ruleConfig), new Properties());
    }

    private DataSource createDataSource(String url) {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl(url);
        ds.setUsername("root");
        ds.setPassword("root123");
        ds.setMaximumPoolSize(20);
        return ds;
    }
}
```

**常见问题与解决方案**

```java
// 1. 跨分片查询（需要汇总）
// ShardingSphere 自动合并结果，但性能较差
// 尽量通过分片键查询

// 2. 跨分片排序
// ShardingSphere 会在内存中排序，大数据量时 OOM
// 建议：避免跨分片 ORDER BY … LIMIT 深度分页

// 3. 事务问题
// 跨分片事务 → 使用分布式事务（SEATA）
@ShardingTransactionType(TransactionType.XA)  // XA 强一致性
@Transactional
public void createOrder(Order order) {
    // 跨分片操作
}

@ShardingTransactionType(TransactionType.BASE)  // BASE 柔性事务
@Transactional
public void updateOrderStatus(Order order) {
    // 基于最终一致性
}
```

**分库分表后的查询限制**

```sql
-- ✅ 支持：带分片键的查询
SELECT * FROM t_order WHERE user_id = 1001;       -- 精确路由
SELECT * FROM t_order WHERE user_id IN (1001, 1002);  -- 广播路由

-- ✅ 支持：不带分片键的查询（会广播到所有分片，性能差）
SELECT * FROM t_order WHERE status = 'PAID';      -- 广播查询

-- ❌ 不推荐：跨分片 JOIN
SELECT * FROM t_order o JOIN t_user u ON o.user_id = u.id;

-- ❌ 不推荐：跨分片 DISTINCT/GROUP BY
SELECT user_id, COUNT(*) FROM t_order GROUP BY user_id;

-- ✅ 解决方案：创建数据库中间表（或应用层聚合）
```

## 三、读写分离

### 3.1 主从复制

MySQL 主从复制是构建读写分离的基础。

**原理**

```text
主库写入 binlog → 从库 IO 线程拉取 binlog → 写入 relay log → SQL 线程重放
```

```text
Master（主库）：
    ↓ 写入 binlog
    ↓
Slave（从库）：
    1. IO 线程：从主库拉取 binlog，写入 relay log
    2. SQL 线程：重放 relay log 中的 SQL
```

**主从配置**

```ini
# my.cnf - 主库配置
[mysqld]
server-id = 1                    # 唯一 ID
log_bin = mysql-bin              # 开启 binlog
binlog_format = ROW              # 推荐 ROW 格式
binlog_row_image = FULL          # 记录完整行数据
expire_logs_days = 7             # binlog 保留 7 天
max_binlog_size = 100M           # 单个 binlog 大小
sync_binlog = 1                  # 每次写入都同步（最安全）
```

```ini
# my.cnf - 从库配置
[mysqld]
server-id = 2                    # 唯一 ID，不能与主库相同
relay_log = mysql-relay-bin      # relay log 文件名
read_only = 1                    # 从库只读（防止误写入）
log_slave_updates = 1            # 级联复制时需要
```

### 3.2 ShardingSphere 读写分离


**Java API 配置读写分离**

### 3.3 主从延迟的解决方案

主从延迟是指主库已经提交的事务，在从库还没有执行完成。常见原因：

```text
原因：
1. 从库硬件比主库差
2. 主库写入压力过大
3. 大事务（一次修改大量数据）
4. 从库执行慢 SQL
5. 网络延迟
```

**解决方案**

```java
// 方案 1：写后读强制读主库（关键业务）
public Order createAndGetOrder(Order order) {
    orderMapper.insert(order);                          // 写入主库
    return readMaster.getOrderById(order.getId());      // 强制从主库读取
}

// 方案 2：缓存标记法（Redis 标记写入时间）
public void createOrder(Order order) {
    orderMapper.insert(order);
    // 在 Redis 中标记该用户的写操作时间
    redisTemplate.opsForValue().set(
            "write:user:" + order.getUserId(),
            System.currentTimeMillis(), 10, TimeUnit.SECONDS);
}

public Order getOrder(Long orderId, Long userId) {
    // 检查该用户最近是否有写操作
    String writeFlag = redisTemplate.opsForValue().get("write:user:" + userId);
    if (writeFlag != null) {
        // 最近有写操作，强制读主库
        return readMaster.getOrderById(orderId);
    }
    // 否则读从库
    return readSlave.getOrderById(orderId);
}

// 方案 3：延迟检测（检查 Seconds_Behind_Master）
// 监测到延迟过高时，临时切到主库读取
// 一般由数据库中间件自动完成

// 方案 4：缩短延迟
-- 从库配置（加快复制）
slave_parallel_workers = 4       -- 并行复制线程数
slave_parallel_type = LOGICAL_CLOCK  -- 基于组提交的并行复制
```
